## 一、规划原则（移动端不是桌面端的缩小版）

桌面端是「坐在电脑前处理数据」，移动端是「在别处突然想起一件事」。这决定四条：

1. **一屏一个任务**。屏幕上同时只做一件事，不要在一个页面塞「列表 + 详情 + 编辑」。
2. **高频操作零跳转**。勾待办、改订单状态这类每天做十次的动作，必须一次点击完成，
   不要「进列表 → 进详情 → 点编辑 → 选状态 → 保存」五步。
3. **查得快比改得多重要**。移动端 70% 的时间是「我看看那个订单到哪一步了」，
   所以列表与详情的加载速度、筛选顺手程度，比功能数量重要。
4. **状态切换 > 完整编辑**（已与维护者确认）。手机上新建成交单、传附件、填 20 个字段，
   误操作成本高、收益低，这类留给桌面端。

| # | 缺口 | 当时的现状 | 影响 |

| 1 | **路由不支持参数** | `findNavByPath()` 只做精确匹配，未知路径直接返回「开发中」占位 | `/orders/:id` 这种详情页**无法实现**，只能靠 query（`/orders?id=x`）凑合，返回时容易丢上下文 |

| 3 | **图标只有 4 个** | `icons.js` 仅 `grid / receipt / bell / gear` | 页面一多就无处安放入口 |

~~建议在写第一个业务页之前，先做一次「路由能力升级」…~~ → 已实际落地为
`config/routes.js`（路径 → 页面的唯一映射）+ `lib/path.js`（唯一的路径归一化）+
`router.js` 的 `goBack()`。

> ⚠️ **勘误**：本节初稿写过「`mobile-rail` 宽 52px，竖向最多舒适容纳 5 项」——**这是错的**。
> 导航栏是纵向排列的，限制条目数的是**高度**不是宽度。实际可用高度约 577px，
> 每项 44px + 6px 间距 = 50px，**理论上能放 11 项**。
> 所以「5 项」是**产品决策**（避免导航栏变成功能清单），不是技术上限。

## 三、导航结构

> ✅ **已定：12 个一级入口，详情页继续从列表进入**（2026-10-22 调整）。
> 早先的「5 个主入口 + 更多」已作废。设置是一级页，不再挂在 `/more` 下面。
> 订单详情、客户详情必须先有一条记录，只放在 `routes.js` 的子页面里，不进导航栏。

导航分成三组，组与组之间有分隔线：

```
业务          工作台 / 订单 / 待办 / 客户
数据与内容    数据看板 / 素材库 / 项目 / 报价单 / 发帖记录
账号与资料    链接收藏 / 账号密码 / 设置
```

备忘录和简历不在这 12 个入口里，留作后续扩展，不要为了「功能齐」再往导航上加。

矮屏、横屏和有底部安全区时，导航栏可以滚动，末尾的设置按钮必须滚得到，当前项保持选中。

### ~~方案 A（已作废）：5 个主入口~~

```
工作台  ──  今日概览 + 记账（已有，需增强）
订单    ──  最高频业务：查进度、改状态
待办    ──  提醒 + 备忘录，勾选即完成
客户    ──  查资料、加跟进、一键拨号
更多    ──  数据看板 / 项目 / 报价 / 素材 / 发帖 / 链接 / 账号 / 设置
```

理由：
- **订单**和**待办**是仅有的两个「每天必看」，必须是一级
- **客户**值得一级：移动端最自然的动作是「给客户打电话/发微信/记一条跟进」，
  这个场景下再进一层「更多 → 客户 → 详情」就废了
- 其余都是「偶尔查」，收进**更多**，避免导航栏变成功能清单
- 现在的**设置**从一级降到「更多 → 设置」（它只有主题切换和退出登录，不值得占一级）

代价：需要扩图标库（已加 `users` / `more`）；5 项占 250px，高度仍然宽裕。

### 详情页形态（已定）

`/orders/:id`、`/customers/:id` 走**独立路由页**，不用底部抽屉：

| | 独立路由页（已选） | 底部抽屉 |
|---|---|---|
| 刷新恢复 | ✅ URL 就是状态 | ❌ 刷新即丢 |
| 微信转发 | ✅ 能直接分享到某张单 | ❌ 只能分享到列表 |
| 返回键 | ✅ 浏览器手势天然可用 | ❌ 要自己劫持 |
| 实现成本 | 需要 router 支持参数匹配（已做） | 简单 |

**右侧导航栏在详情页保持可见**，不做隐藏。理由：详情页也要能一键跳去别的模块，
藏起来反而多一步；后续若某个页面需要整屏（如带底部操作条的编辑页），
再给路由加 `hideRail` 开关，现在不做 —— 用不上的开关就是负债。

### ~~方案 B（保守）：保持 4 个一级~~（已否决）

`工作台 / 订单 / 待办 / 更多`，客户收进「更多」。

优点：不动现有结构，改动最小。缺点：客户场景多一次跳转。
如果客户使用频次不高，选 B 也完全合理 —— **这一条需要维护者拍板**。

## 五、P0 页面的关键设计点

### 订单列表 `/orders`

- **筛选**：订单状态、付款状态、已逾期，三条都可以点；关键词走后端 `keyword`
- **卡片信息密度**（一屏 3-4 张，不要 8 张）：
  - 第一行：客户昵称 · 项目名（超长省略）
  - 第二行：金额（大）+ 订单状态徽标 + 付款状态徽标
  - 第三行：截止日期（`describeDeadline` 输出「逾期 3 天」/「明天到期」）
- **下拉刷新 + 上拉加载**：直接用 `createListView`，不要重写
- **搜索**：`keyword` 参数后端已支持，放在顶栏搜索按钮里

### 订单详情 `/orders/:id`

- **字段分组**（不要平铺 30 个字段）：
  1. 概要卡：项目名、金额、状态徽标
  2. 客户卡：昵称/真实姓名/电话（点击拨号）/来源/标签
  3. 时间节点卡：接单 / 需求确认 / 初稿 / 终稿（用时间轴，逾期标红）
  4. 商务卡：成本、耗时、净利率、时薪
  5. 附件卡：`uploadedFiles` 缩略图（注意 `<img>` 只能靠 Cookie 鉴权）
- **状态切换放底部固定操作条**，不塞进详情里滚动：点状态 → 底部弹层选目标状态 → 立即生效 + toast
  （后端 `PUT /orders/:id` 是白名单 merge，只传 `orderStatus` 安全）

### 待办 `/todo`

- **按时间分组，不按创建时间**：`已逾期` / `今天` / `本周` / `以后` / `已完成`
- **勾选即完成**，不要二次确认（可撤销：3 秒内点 toast 上的「撤销」）
- 逾期组默认展开且置顶，带红色计数

### 工作台增强 `/`

现有工作台是「开发小账」（收支视角）。移动端首页应该回答**「今天要干什么」**：

```
[ 今日概览 ]
  今日收入 ¥xxx   本月 ¥xxx（环比 +12%）
  待处理：3 个待验收 · 2 个今日到期 · 8 条逾期提醒
  未读通知 10 条  →
[ 收支卡片组 ]（保留现有）
[ 最近记录 ]（保留现有）
[ 记一笔 ]（保留现有 FAB）
```

在现有页面上**插入概览区**即可，不推翻重做。

## 七、明确不做（避免范围膨胀）

| 不做 | 原因 |
|---|---|
| 新建/编辑完整订单 | 表单字段 30+，手机上填易错；桌面端已有 |
| 上传附件、编辑图片 | 同上，且移动端图片处理成本高 |
| 编辑客户资料、删除记录 | 破坏性操作放桌面端，降低误触风险 |
| 报价单生成/PDF | 需要精细排版，手机屏幕不适合 |
| 账号密码编辑 | `accounts` 返回解密凭据，移动端只读脱敏 |
| 离线写入队列 | 当前 PWA 只做 API 短缓存；写操作离线同步是独立课题 |

## 八、与桌面端的一致性约束

移动端和桌面端不共享代码，但**必须共享契约**，以下改动要两边同步：

- 订单状态枚举：`pending / processing / acceptance / completed / closed`
  （与 `backend/src/utils/order-payload.js`、`frontend` 的 `ORDER_STATUSES` 三处一致）
- 付款状态是**中文枚举**：`未付款 / 部分付款 / 已结清`
- 金额口径：只统计已付款订单（`paidAmount`），移动端所有统计直接取后端结果，**不要自己算**
