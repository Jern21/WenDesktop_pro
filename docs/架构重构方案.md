# 架构重构方案：原生 JS 真 SPA

> 目标：**不引入框架、不引入构建工具**，把 18 个独立 HTML 文档改造成单一入口的真 SPA，提高复用率，为后续迭代和服务器部署打底。

## 一、现状诊断（实测数据，非估算）

| 指标 | 实测值 | 问题定性 |
|---|---|---|
| HTML 入口文档 | 19 个（index + pages/ 下 18） | 每个自带完整 head，样板重复 |
| 页面总行数 | 15,603 行 | — |
| head 资产引用 | 每页约 6 行，共 ~108 行 | 加一个全局资源要改 18 个文件 |
| 内联 `<style>` 块 | 约 590 行分散在 19 个文件 | 需动态注入，靠正则 sniffing 定位 |
| `escapeHtml` 定义 | **3 套不同实现** | 其中 customer 那套**未转义引号 → XSS 缺口** |
| `showToast` 定义 | **4 套完全不同实现**（连 DOM id 都不同） | 同名不同行为 |
| `renderPagination` | 3 套（customer / orders / platform） | 分页逻辑重复三遍 |
| 跨页面同名函数 | 15 组以上 | 详见表下 |
| `onclick` 内联事件 | 77 处（仅 6 个页面） | 其余 12 页已是事件绑定模式 |
| `window.ui` 公共层 | **存在**（195 行，含 toast/confirm） | **但 10 个页面没用它，全在复制自己的 showToast** |

### 跨页面同名函数（改成真 SPA 后会互相覆盖）

```
escapeHtml      12 个页面    showToast       10 个页面
init             9 个页面    fallbackCopy     6 个页面
formatDate       4 个页面    closeModal       3 个页面
renderPagination 3 个页面    formatMoney      2 个页面
updateDetailPanel / renderEmptyDetailPanel / setText / copyText / showMenu / closeMenu ...
```

**为什么现在没出问题**：伪 SPA 切页时只替换 `#page-view` 的 innerHTML，旧页面 DOM 已不存在，即使函数被同名覆盖也「恰好」调不到。**这是隐式巧合，不是设计。** 一旦改成真 SPA 多 view 共存，覆盖顺序决定行为，属静默故障。

### 必须清掉的三处 hack

| 位置 | hack | 正确解法 |
|---|---|---|
| `spa-router.js:333` | 内联脚本 `let/const` 正则转 `var` | 脚本独立成文件 + IIFE 封装，自然作用域隔离 |
| `spa-router.js:119` | 正则嗅探 `.hidden {` 定位 Tailwind style 插入点 | 样式全部合并进 CSS 静态引入 |
| `spa-router.js:209` | `cleanupGlobalOverlays()` 手工扫残留浮层 | 组件统一 registry，unmount 自动清理 |

## 二、目标架构

### 核心原则

1. **单一入口**——`index.html` 只写一次 head 和壳层
2. **view 契约化**——每个页面 = 一个 view 模块，生命周期固定为 `mount/unmount`
3. **复用层强制化**——工具、UI、表格只能走 `core/`，禁止页面内重复定义
4. **零构建**——保持「改完刷新即生效」的迭代习惯
5. **绞杀者迁移**——新旧共存，逐页替换，**任何时刻系统都可用**

### 目录结构

```
frontend/
├── index.html                 # 唯一入口：公共 head + 侧边栏 + 顶栏 + #page-view
├── css/
│   ├── common.css             # 已有，继续用
│   └── views.css              # 各页面级样式合并（消灭动态注入）
├── js/
│   ├── core/                  # ★ 新增：框架层（不依赖任何页面）
│   │   ├── dom.js             # 安全转义、DOM 工具、事件委托、格式化
│   │   ├── ui.js              # toast / confirm / modal / loading（唯一实现）
│   │   ├── view.js            # 生命周期 + cleanup 自动收集
│   │   ├── router.js          # 路由注册、模板缓存、前进后退
│   │   └── api.js             # 已有 265 行，原样并入
│   ├── components/            # 跨页面复用组件
│   │   ├── sidebar.js  header.js  avatar.js  platform-icons.js  theme.js
│   │   └── table.js           # 表格 + 分页（收编 3 套实现）
│   ├── views/                 # ★ 每个页面一个模块
│   │   ├── orders.js  customer.js  quote.js  ...
│   └── app.js                 # 启动入口：注册路由 → 初始化壳层
├── views/                     # ★ 页面模板（HTML 片段，保留可读性）
│   ├── orders.html  customer.html  ...
└── assets/                    # 原样不动
```

> **为什么模板保留 .html 而不是塞进 JS 字符串**：保住编辑器语法高亮、Tailwind 类名提示和 diff 可读性。运行时 `fetch` 一次后进内存缓存，二次切换零网络开销。

### view 生命周期契约

```js
App.view('orders', {
    title: '我的订单',
    template: 'views/orders.html',

    async mount(root, ctx) {
        this.orders = await App.api.get('/orders');
        this.render(root);
        // 注册的清理函数会在离开页面时自动执行
        ctx.onCleanup(() => clearInterval(this.pollTimer));
    },

    unmount() {
        // 兜底清理（一般用 ctx.onCleanup 就够了）
    }
});
```

**`ctx.onCleanup()` 是根治内存泄漏的关键**：定时器、事件监听、ECharts 实例、`window` 上的全局监听，全部登记后由框架在切换时统一执行。不再依赖 `cleanupGlobalOverlays()` 那种手工扫描兜底。

## 三、迁移路线（绞杀者模式）

**原则：每一步做完系统都能正常用，出问题单步回滚。**

| 阶段 | 动作 | 系统可用性 |
|---|---|---|
| S1 | 建立 `core/` 框架层，不接入 | 完全不受影响 |
| S2 | 改造 `index.html` 为唯一入口 + 新路由接管 1 个页面 | 新旧共存 |
| S3 | 按页面逐个迁移，迁完一个删一个旧文件 | 新旧共存 |
| S4 | 全部迁完，删除 `spa-router.js` 和旧页面 | — |
| S5 | 后端加鉴权、收紧 CORS | — |

### URL 方案

采用 **History API**（非 hash），保留可读 URL：

```
/                    → 仪表盘
/orders              → 订单
/orders/:id          → 订单详情
/customer            → 客户
```

服务端**已正式切换到 `app.html`**：

```
/ 、/index.html        → app.html（首页走新 SPA）
未命中任何实际文件时   → app.html（由前端路由决定渲染哪个视图 / 404）
旧页面文件 /pages/**   → 仍可直接访问（保留作回退）
```

部署到 Nginx 时对应补一行：

```nginx
location / { try_files $uri $uri/ /app.html; }
```

### 迁移中发现并修掉的真实缺陷

1. **深链接全部失效（最严重）**
   `app.js` 的 `bootstrap()` 在 `router.start()` 之前调用 `router.match()`，
   而路由表要到 `start()` 内部才从已注册视图收集 —— 那时表是空的，
   于是任何路径都匹配不到，一律兜底到第一个视图。现象：刷新 `/orders` 看到首页。
   修复：`match()` 惰性调用 `collectFromViews()`。

2. **`accounts` 的动态卡片按钮全部失效**
   `viewAccount / editAccount / deleteAccount / copyText` 是局部函数，
   JS 拼接的 `onclick` 在全局作用域找不到它们。

3. **旧全局 `ui` 缺失**
   `dashboard` 等 5 个视图调用 `ui.toast.error()`、`ui.showLoading()`，
   但新入口没加载 `js/ui-components.js`，直接 `ReferenceError`。
   修复：在 `core/ui.js` 里让 `window.ui` 转接 `App.ui`（一套实现，两套 API）。

4. **`spa:ready` 的 `detail.page` 不匹配旧守卫**
   旧代码普遍写 `if (page.indexOf('stats') === -1) return;`，
   而新路由派发的是视图名（`stats` / `dashboard`），dashboard 的 `isHomePage()`
   只认 `index` / `home` → 全部不执行。修复：派发 `def.nav`（`index.html`）。

5. **`DOMContentLoaded` 监听永不执行**
   SPA 切页时该事件早已触发过。批量改造成「未就绪则监听，已就绪立刻执行」。

6. **`spaNavigate` 未定义**
   `header.js`（通知跳转）和 `canvas.html`（去配置）都调它，
   新入口没有这个函数，点了等于没反应。修复：`app.js` 补兼容层。

7. **相对路径在深路径下算错**
   旧代码大量 `(ROOT_URL || PAGE_BASE || '') + 'assets/...'`，两者为空时是相对路径。
   修复：入口统一置 `PAGE_BASE = ROOT_URL = '/'`。

8. **`@apply` 依赖 Tailwind CDN 运行时展开**
   SPA 动态注入的样式表不保证被处理 → 6 个 CSS 文件全部展开为原生 CSS。

9. **`asyncHandler` 抓不住同步抛错（写接口时才发现）**
   `Promise.resolve(fn(...))` 里 `fn` 是同步执行的，只要它同步 throw，
   异常在进入 `.catch()` 之前就逸出 → Express 默认错误页（HTML + 完整堆栈）。
   现象：订单校验改成 throw 之后，前端 `res.json()` 报 `Unexpected token '<'`。
   修复：`Promise.resolve().then(() => fn(...))`，并采纳 `err.status`。

10. **`PUT /api/orders/:id` 能把记录改成另一个 id**
    `Object.assign({}, body)` 直接当 patch + `Storage.update()` 的 `Object.assign({}, old, patch)`
   → 请求体带 `id` 就能"改名"记录：原 id 查不到，新 id 重复。
   修复：白名单 + 共用校验，见上文「订单写入的唯一入口」。

### 关键机制：全局键快照回收

旧代码为了配合内联 `onclick`，会把处理函数挂到 `window`（`window.prevPage = prevPage`）。
保留这些赋值 → 内联 onclick（含 JS 拼接的）继续可用；但会跨页残留闭包。

`core/view.js` 的做法：`mount` 前对 `window` 的自有键集拍快照，卸载时删除「本次新增的键」。
既是兼容层，也是泄漏防线，且第三方库（`echarts` / `pdfjsLib` 等）在 `KEEP_GLOBALS` 白名单里不会被误删。

### 入口分流是怎么做的（改这里之前先读）

`backend/server.js` 里加了一个**位置很讲究**的中间件：

```js
app.use(auth.pageGuard());          // ① 鉴权必须先跑
app.get(['/', '/index.html'], …)    // ② 首页分流
app.use(express.static(frontendDir)); // ③ 静态托管
app.get('*', …)                     // ④ SPA 回退到 app.html
```

两个约束缺一不可：

1. **必须在 `pageGuard` 之后** —— 否则首页会绕过登录，谁都能进。

### 共享表单模块的约定（新增抽屉/弹窗时照这个写）

`js/order-form.js`、`js/poster-form.js`、`js/memo-form.js` 这类「自己建 DOM 的抽屉」，
在 `app.html` 里**只加载一次**，不挂在任何 view 下。因为它们自己管 DOM 的创建与销毁，
并监听 `spa:cleanup-forms` 重置状态，跟着视图反复初始化反而会重复绑事件。

约定（不加这几条就会出「点了没反应」或空引用崩溃）：

1. **必须暴露全局入口**，如 `window.openOrderForm` / `window.closeOrderForm`。
   视图里普遍写的是 `if (typeof window.openXxx === 'function') …`，
   **模块没加载时是静默跳过，页面不报任何错** —— 这是本项目最坑的一类故障，
   所以改完务必跑 `node tools/verify-deps.js`。
2. **销毁只能有一个入口**：`destroyDrawer()`。关闭动画的定时器和
   `spa:cleanup-forms` 都调它，不要两处各写一遍「置 null + 复位 isOpen」，
   否则先跑的置空、后跑的拿 null 去点 `classList`。
3. **动画用的 `requestAnimationFrame` 回调不能裸吃模块级变量**：
   回调是异步的，执行时节点可能已销毁。用局部引用 + `isConnected` 判断。
4. **复位 `body.overflow` 前先确认自己确实持有锁**，否则会把别的模块的滚动锁解开。
5. ESC 之类的 `document` 级监听要挂在模块级，不要写在「每次打开都调用」的
   `bindEvents()` 里，否则开 N 次叠 N 个监听。
6. **「已打开就跳过」的守卫要区分「真的开着」和「正在关闭」**：
   关闭动画 300ms 内 `isOpen` 仍为 true，若直接 `if (isOpen) return;`，
   这段时间里再点「编辑」会静默无反应 —— 和「打不开」的症状一模一样。
   正确做法：有 `closeTimer` 就 `destroyDrawer()` 后继续打开新的，没有才跳过。

### 视图 CSS 的优先级约定（新增样式前必读）

**症状**：提醒页打开就满屏遮罩，「确认删除」盖在最上面，点页面任何地方都像在点删除。

**成因**（不是 JS 的锅，JS 只切 `hidden` 类）：

1. 视图 CSS 由 `core/router.js` 的 `ensureStyle()` **动态 append 到 `<head>`**，
   位置排在 `tailwind.min.js` 运行时注入的 `<style>` **之后**；
2. `css/views/reminder.css` 里写的是孤立的单类选择器 `.modal-overlay { display: flex }`；
3. Tailwind 的 `.hidden { display: none }` 与它**同为 0,1,0 优先级**，同优先级下后注入者胜；
4. 于是 `.hidden` 被压掉 → 三个全屏遮罩从首屏起就全部可见并层叠，
   `#delete-modal` 在最上层，**每一次点击都先落到「确认删除」的遮罩上**。

**约定**：视图 CSS 里凡是要给某个类设 `display`，而该类元素**可能带 `hidden`**，
必须用下面两种写法之一，把优先级抬到 0,2,0，不再依赖样式表加载顺序：

```css
/* 写法一：非 hidden 时才设 display（推荐，一条规则不分裂） */
.modal-overlay:not(.hidden) { display: flex; }
.modal-overlay.hidden { display: none !important; }

/* 写法二：给 hidden 单独兜底 */
.foo.hidden { display: none !important; }
```

现有可参照的实现：`css/views/project.css`（`.project-kanban-board`）、
`css/views/reminder.css`（`.modal-overlay`）。

**两道自动检查**：

- `node tools/verify-consistency.js` —— 静态扫「模板里同一 `class` 属性既带 `hidden`、
  又带某个被视图 CSS 设了 `display` 的类」，缺加固就 FAIL；
- `test/_probe-hidden-audit.html` —— 浏览器里遍历 18 个视图的每个元素，实际加一次 `hidden`
  看是否真的隐藏。分级报告：**初始就漏 = 正在发生的故障**，
  **加 hidden 无效 = 潜在风险**（当前没坏，以后加 `hidden` 会坏）。

### SPA 全局回收与外部脚本的契约（新增动态脚本前必读）

`core/view.js` 的 `restoreGlobals()` 会在离开视图时，把**挂载期间新增的 `window` 自有键**全部删掉。
这对防止跨页泄漏是必要的，但它和「按需加载的外部脚本」有一处天然冲突：

外部脚本只加载**一次**，而它挂在 `window` 上的入口函数，第一次离开时就被清掉了。
于是第二次进入页面，按钮一点就是 `Uncaught ReferenceError`。

**哪些会出问题**（判据：动态加载 + IIFE 顶层赋值）：

| 脚本 | 来源 | 挂载方式 | 会失效？ |
|---|---|---|---|
| `js/project-page.js` | `views/project.js` 按需 append | `window.openEditForm = …`（IIFE 顶层） | **会**（已修） |
| `js/views/*.js` | `app.html` 静态引入 | mount 内赋值，每次挂载重跑 | 不会 |
| `js/platform-manager.js` | `app.html` 静态引入 | 首屏就执行，早于第一次快照 | 不会 |

**正确写法**（以 project 为例，新增动态脚本照抄）：

```js
// ① 脚本侧：把全局入口收进可重复执行的函数，并暴露一个契约对象
function exposeGlobals() {
    window.openEditForm = function (name) { openEditForm(name || null); };
}
function init() { exposeGlobals(); /* ... */ }
window.__projectPage = { init, exposeGlobals };

// ② 视图侧：加载完把契约对象抓进自己的闭包（window 上的引用会被清，闭包不会）
}).then(function () { pageApi = global.__projectPage; });

// ③ 每次 mount 都补一次
if (pageApi) pageApi.exposeGlobals();
```

**防重复绑定的哨兵不要再挂 `window`**：`window.__xxxBound` 会被回收掉，而
`addEventListener` 注册的监听删不掉 —— 哨兵没了、监听还在，状态就脱节了。
改挂 `document`（不在回收范围内），参见 `project-page.js` 的 `document._projectPageSpaReadyBound`。

回归工具：`test/_probe-project-globals.html`（走 project → orders → project 三轮，
每轮都真的点一次「新建项目」并断言弹窗出现）。

### 用户数据归属迁移：不能在启动时自动跑（改数据布局前必读）

`utils/user-data-migrate.js` 干的事是：**把根目录 `data/*.json` 的归属改成 trial**，
原文件搬进 `_legacy_root_data/`，其他账号置空。

它**不是**启动流程的一部分，只能显式执行：

```bash
node backend/src/utils/user-data-migrate.js        # 手动跑一次
USER_SCOPE_MIGRATE=1 node backend/server.js        # 部署脚本明确要求时才自动跑
```

为什么不能挂在启动钩子里（原来就是这么写的，已改）：

- 任何新数据目录首启都会被搬一遍 —— **测试临时目录、换机器、全新部署**；
- 全新部署时，示例数据会不声不响全归到**免密**的 trial 账号，`admin` 进去空无一物；
- `admin` 若已经存了真实数据，会被直接清空。

顺带加的安全网：**置空任何账号之前，先把它的非空数据备份到
`_legacy_root_data/admin-backup-<时间戳>/`**。判断"有没有数据"时，
空数组、空设置模板不算；**解析失败或结构不是数组的文件算有数据**（宁可多备份一份）。

两者的分工别混：

| 迁移 | 频率 | 原因 |
|---|---|---|
| `secret-migration.runAll()` 字段加密 | **每次启动** | 幂等，必须保证任何请求读到的都是密文 |
| `user-data-migrate` 数据归属 | **手动 / 显式开关** | 一次性改数据，自动跑会误伤新环境 |

### 请求层与存储层的两条硬规则

**1. 写请求不许自动重试**（`js/api.js`）

原来任何方法失败都重试。但服务端可能**已经写入成功、只是响应丢在路上**，
重试就会重复创建一条订单/付款/客户记录 —— 比报错难查得多。
现在只有 `GET/HEAD/OPTIONS` 自动重试；确实幂等的写请求用 `retryUnsafe: true` 显式开启。

同时修了两处：
- `config.retryCount || CONFIG.retryCount` 改成「有没有传」，否则 `retryCount: 0`（不重试）会被静默替换成默认值；
- `CONFIG.timeout` 原来**根本没实现**（代码里没有 AbortController），现在补齐，并把调用方 `signal` 转发进 fetch。

**2. 数据文件读不懂就抛，绝不返回 `[]`**（`utils/storage.js`）

`Storage` 的写路径都是「`_read()` → 改内存 → `_write(全量)`」。
一旦 `_read()` 把「解析失败」当成空数组返回，下一次写入就用新数据覆盖整个文件 ——
**数据损坏被伪装成没有数据，且零告警**。
现在只有「文件不存在」和「文件是空的」算空数据，其余抛 `StorageError`；
`recoverFromBackup()` 提供显式恢复入口（会自动挑最新一份**能解析成数组**的备份，
不盲信最新那份 —— 它可能就是在数据坏掉之后拍的）。

注意：`auth.json` / `settings.json` 是对象结构且不走 `Storage`，不受影响。

### 订单写入的唯一入口：`utils/order-payload.js`（改订单接口前必读）

**所有** 订单字段的归一化与校验只在这里做，`POST /api/orders` 与
`PUT /api/orders/:id` 共用同一份规则。

为什么必须这样：`PUT` 原来是 `Object.assign({}, body)` 直接当 patch 用。
而 `Storage.update()` 内部是 `Object.assign({}, old, patch)`，
所以请求体里带 `{"id": "别的id"}` 就能**把记录改成另一个 id**：

- 原 id 从此查不到（前端表现是"订单凭空消失"）；
- 新 id 若已存在，文件里就出现两条同 id 记录（`findById` 只认第一条）。

同时 `PUT` 完全没有业务校验，可以把成交金额改成 0、客户昵称清空、
状态改成一个前端字典里不存在的值（统计页 `statusCounts` 会直接漏掉它）。

现在的约定：

| 概念 | 规则 |
|---|---|
| `EDITABLE_FIELDS` | 只有这 23 个字段能被写进数据文件，其余丢弃并 `console.warn` |
| `PROTECTED_FIELDS` | `id` / `createdAt` / `updatedAt` / `orderNo` 永不接受客户端输入 |
| `orderNo` | 一律 `generateOrderNo()` 生成（客户端能指定就能造重复单号，序号推算会永久错位） |
| 必填校验 | 创建校验全量；更新只校验**本次真正提交的字段** |
| 为什么更新不校验全量 | 历史脏数据（如 `projectName: ''`）若一并校验，那张订单会彻底不可编辑 |
| 付款比例 | 由「打款记录 / 成交额」推导，不信任客户端算好的值 |
| 枚举 | `orderStatus` / `paymentStatus` 非法直接 400（这两个驱动所有统计口径） |

### `asyncHandler` 的两个陷阱（写新路由前必读）

```js
// ❌ 错：fn 是同步执行的，同步抛错时异常在进入 .catch() 之前就逸出了
Promise.resolve(fn(req, res, next)).catch(...)

// ✅ 对：把调用放进 promise 链里
Promise.resolve().then(function () { return fn(req, res, next); }).catch(...)
```

踩过的现象：校验函数一改成「直接 throw」，接口就返回 **HTML 错误页 + 完整堆栈**
（Express 默认错误处理），前端 `res.json()` 报 `Unexpected token '<'`。
之前没暴露，是因为老代码都用 `return resp.error(...)` 不抛异常。

第二个：`err.status` 现在会被采纳（`OrderPayloadError` 带 400）。
否则业务校验失败会被当成「服务器内部错误」——前端弹"服务器异常"，
日志里 400 和真故障混在一起，排查时误判。
